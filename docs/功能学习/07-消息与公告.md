### 1. 统一响应体 `{ code, msg, data }`

`backend/common/response.py:29-36`：

```python
def ok(data=None, msg='success'):
    """成功响应：业务码固定 200，data 可以是对象、列表或 None。"""
    return Response({'code': 200, 'msg': msg, 'data': data})  # HTTP 状态恒为 200，业务码放在 body 里


def fail(msg='error', code=500, data=None):
    """失败响应：自定义业务码与提示文案，便于前端按 code 分支处理。"""
    return Response({'code': code, 'msg': msg, 'data': data})  # 同样不改 HTTP 状态，前端只看 body
```

```python
class BigIntJSONRenderer(JSONRenderer):
    """全局 JSON 渲染器：雪花主键以字符串输出，前端回传时不再丢精度。"""

    def render(self, data, accepted_media_type=None, renderer_context=None):
```

### 2. 统一分页结构 `{ total, page, page_size, list }`

`backend/common/pagination.py:27-37`：

```python
def paginate(self, queryset, serializer_class=None, many=True):
    """统计总数并截取当前页，可选序列化后按统一结构返回。"""
    total = queryset.count()                      # 先 COUNT，前端据此算总页数
    rows = queryset[self.offset:self.offset + self.page_size]  # LIMIT offset, page_size
    data = {
        'total': total,                           # 总记录数
        'page': self.page,                        # 当前页码
        'page_size': self.page_size,              # 每页条数
        'list': serializer_class(rows, many=many).data if serializer_class else list(rows),
        # 有序列化器就逐条转字典；没有则退化为原始行
    }
    return ok(data)                               # 再包一层 {code, msg, data}
```

分页参数解析在 `backend/common/pagination.py:12-20`：`page` 最小为 1，`page_size` 限制在 1~1000，非法值回退 `settings.PAGE_DEFAULT_SIZE`（`backend/config/settings.py:112` 配置为 10）。

> Java 对照：等价于 `PageHelper.startPage(page, pageSize)` + `PageInfo.total/list`，只是这里手写 `count` 与切片。

### 3. 登录、权限与 ViewSet 基类

- 认证：`backend/common/auth.py:35-62` 的 `JWTAuthentication` 解析 `Authorization: Bearer <token>`，把用户挂到 `request.user_info`；账号被删除/停用时旧 token 立即失效。
- 登录校验：`backend/common/auth.py:65-72` 的 `LoginRequired`，没有 `user_info` 就抛 401。
- 权限校验：`backend/common/permissions.py:43-59` 的 `PermissionCheck`，按 `view.perm_map` 把 action 映射成权限标识（如 `msg:list`），超管角色 `admin` 拥有 `*:*:*` 通配。
- CRUD 基类：`backend/common/views.py:11-124` 的 `CrudViewSet`，统一提供 `list/create/update/delete/status`，子类只声明 `model / serializer_class / perm_prefix / filter_map / order_by / module_name`。

`backend/common/views.py:30-40` 动态生成权限表：

```python
@property
def permission_classes(self):
    """按 perm_prefix 动态生成 perm_map，并固定使用 PermissionCheck。"""
    prefix = self.perm_prefix                        # 例如 'msg'
    self.perm_map = {
        'list': f'{prefix}:list',                    # 列表权限
        'create': f'{prefix}:create',                # 新增权限
        'update': f'{prefix}:update',                # 编辑权限
        'delete': f'{prefix}:delete',                # 删除权限
    }
    return [PermissionCheck]                          # 登录校验已包含在 PermissionCheck 内部
```

> 关键细节：`perm_map` 只登记了 `list/create/update/delete` 四个动作。所有自定义动作（`my`、`read`、`read_all`、`status`、`publish`、`read`）在 `perm_map` 中查不到，`PermissionCheck` 会直接返回 `True`，**只校验登录，不再校验按钮权限**。这一点会在各示例中反复出现。

`backend/config/urls.py:12-13` 把两个模块挂到 `/api` 下：

`backend/apps/msg/urls.py:7-38` 与 `backend/apps/notice/urls.py:7-30` 都使用了一个本地 `crud()` 工厂函数，把同一套「list/create/delete/update」路径按资源前缀批量生成。它的核心是 `viewset.as_view({...})`：同一个 URL 按 HTTP 方法分派到不同动作。

```python
def crud(prefix, viewset, extras=None):
    def _join(s): return f'{prefix}/{s}' if prefix else s   # 拼接“资源前缀/动作”
    list_view = viewset.as_view({'get': 'list', 'post': 'create', 'delete': 'delete'})
    # 同一个入口：GET=列表、POST=新增、DELETE=批量删除
    item_view = viewset.as_view({'put': 'update'})           # 详情入口只接受 PUT
    patterns = [
        path(_join('list'), list_view),                      # /资源/list
        path(_join('create'), list_view),                    # /资源/create
        path(_join('delete'), list_view),                    # /资源/delete
        path(_join('update/<int:pk>'), item_view),           # /资源/update/主键
    ]
    for suffix, methods in (extras or {}).items():           # 追加自定义动作
        patterns.append(path(_join(suffix), viewset.as_view(methods)))
    return patterns
```

> Java 对照：`urls.py` 相当于 `@RequestMapping` 类级前缀 + 方法级 `@GetMapping/@PostMapping`；`as_view({'get': 'list'})` 相当于按 HTTP 方法路由到 Controller 方法。

#### 视图业务逻辑

`backend/common/views.py:42-61`：

```python
def get_queryset(self):
    """返回过滤逻辑删除后的基础查询集，供各类操作复用。"""
    return self.model.objects.filter(is_deleted=0).order_by(self.order_by)
    # 所有业务表统一按 is_deleted=0 过滤；排序用子类声明的 -id

def apply_filters(self, queryset, request):
    """按 filter_map 把非空查询参数拼成 ORM 过滤条件。"""
    for param, lookup in self.filter_map.items():
        value = request.query_params.get(param)     # 从 URL 查询串取值
        if value not in (None, ''):                 # 空串/null 视为不筛选
            queryset = queryset.filter(**{f'{param}__{lookup}': value})
            # 动态拼成 template_name__icontains=xxx 这类 ORM 条件
    return queryset

def list(self, request):
    """列表接口：筛选 + 分页 + 序列化。"""
    queryset = self.apply_filters(self.get_queryset(), request)  # 先过滤，保证 total 准确
    return StandardPagination(request).paginate(
        queryset, self.get_serializer_class())   # 再分页并序列化
```

```python
@action(detail=False, methods=['get'])
def my(self, request):
    """我的消息：按当前登录用户 filter receiver_id 并分页。"""
    user = getattr(request, 'user_info', None)   # JWT 认证阶段挂上的当前用户
    if not user or not getattr(user, 'id', None):
        return fail('未登录', code=401)           # 理论上 PermissionCheck 已拦截，这里再兜底
    queryset = self.apply_filters(
        MsgRecord.objects.filter(receiver_id=user.id, is_deleted=0).order_by('-id'),
        # 只查“接收人=我”且未逻辑删除的消息
        request)                                  # 复用基类过滤：仍可按 title/msg_type 筛选
    return StandardPagination(request).paginate(queryset, MsgRecordSerializer)
    # 统一分页返回 {total,page,page_size,list}
```

#### 视图业务逻辑

- 权限：`detail=False` 表示集合动作；`perm_map` 中没有 `my`，所以只校验登录（`PermissionCheck` 对未知 action 直接放行）。
- 身份来源：不是前端传 `receiver_id`，而是后端从 `request.user_info.id` 取当前用户，避免越权查看他人消息。
- 过滤：固定 `receiver_id=当前用户` + `is_deleted=0`，再叠加 `filter_map`（`backend/apps/msg/views.py:35-40`）：

```python
filter_map = {
    'title': 'icontains',      # 标题模糊搜索
    'msg_type': 'exact',       # 消息类型精确匹配
    'receiver_id': 'exact',    # 理论上可传，但与固定条件叠加后只会过滤到同一人
```

```python
@action(detail=True, methods=['post'])
def read(self, request, pk=None):
    """标记单条消息为已读。"""
    affected = MsgRecord.objects.filter(pk=pk, is_deleted=0).update(
        is_read=1,                                        # 直接置为已读
        read_time=time.strftime('%Y-%m-%d %H:%M:%S'))     # 用本地时间字符串，和手工 SQL 格式一致
    # 一条 UPDATE 完成，返回受影响行数
    if not affected:                                      # 0 行 = 记录不存在或已逻辑删除
        return fail('消息不存在', code=404)                # 业务码 404，HTTP 仍 200
    return ok(None, '已标记为已读')                        # data=None，仅返回提示
```

#### 视图业务逻辑

- **没有校验消息归属**：任何已登录用户只要知道 `pk`，都能把别人的消息标记为已读。这是一个越权风险点（见文末问题清单）。
- **没有细粒度权限**：`perm_map` 里没有 `read`，`PermissionCheck` 对未知 action 放行，只要求登录。
- **不做序列化器校验**：直接走 `QuerySet.update()`，绕过 `MsgRecordSerializer`，因此也绕过了字段校验。
- **幂等性**：重复调用仍返回成功，`read_time` 会被刷新为最新时间。
- **逻辑删除过滤**：`is_deleted=0`，已删除消息返回 404。

#### 数据表与 ORM/SQL

表：`msg_record`（同示例 56）。本次只更新两列：

```sql
UPDATE msg_record
SET is_read = 1,
    read_time = '2026-11-06 10:30:00'
WHERE id = %s
  AND is_deleted = 0;
```

> ORM 细节：`MsgRecord.objects.filter(...).update(...)` 不会触发 `save()`，不会自动写 `update_by/update_time`，所以这次已读操作不会留下审计字段。对“已读”这种高频低价值写操作，这是有意的轻量实现。

| Django | Java/Spring 对应 |
| --- | --- |
| `@action(detail=True, methods=['post'])` | `@PostMapping("/read/{id}")` |

```python
@action(detail=False, methods=['post'])
def read_all(self, request):
    """全部标记为已读。"""
    user = getattr(request, 'user_info', None)        # 当前登录用户
    if not user or not getattr(user, 'id', None):     # 未登录直接拒绝
        return fail('未登录', code=401)
    affected = MsgRecord.objects.filter(
        receiver_id=user.id,                          # 只处理“我的”消息
```

```python
def status(self, request, pk=None):
    """启用/停用：按请求体的 status 或 enabled 字段更新指定记录。"""
    instance = self.get_queryset().filter(pk=pk).first()   # 只在未删除数据中查找
    if not instance:
        return self._not_found()                            # 业务码 404
    data = request.data or {}                               # 兼容空请求体
    fields = [f for f in ('status', 'enabled') if f in data]
    # 兼容两种字段名：模板/分类用 status，推送渠道用 enabled
    if not fields:
        return fail('未提供状态字段', code=400)              # 参数缺失明确提示
    for field in fields:
        setattr(instance, field, data[field])               # 逐个赋值
    user = getattr(request, 'user_info', None)
    if hasattr(instance, 'update_by'):
        instance.update_by = user.username if user else ''  # 审计：更新人
    if hasattr(instance, 'update_time'):
        instance.update_time = time.strftime('%Y-%m-%d %H:%M:%S')  # 审计：更新时间
    instance.save()                                          # 只保存本次改动
    return ok(self.serializer_class(instance).data, '状态更新成功')
```

#### 视图业务逻辑

- 定位：`get_queryset()` 过滤 `is_deleted=0`，已删除渠道改不了。
- 字段兼容：同时支持 `status` 与 `enabled`，所以模板启停和渠道启停共用同一个基类方法。
- 只更新提交字段：`setattr` 只对请求体里出现的键执行，避免整对象 `save()` 覆盖其他列。
- 审计：`update_by` 取 `user.username`，`update_time` 取当前时间字符串。
- **权限缺口**：`status` 不在 `perm_map`，后端只校验登录；前端 `v-perm="'msg:update'"` 只是隐藏按钮，不能阻止直接构造请求。

```python
@action(detail=True, methods=['put'])
def publish(self, request, pk=None):
    """发布公告：置为已发布并记录发布人与发布时间。"""
    row = NoticeInfo.objects.filter(pk=pk, is_deleted=0).first()
    # 只允许发布未逻辑删除的公告
    if not row:
        return fail('公告不存在', code=404)     # 不存在返回业务码 404
    user = getattr(request, 'user_info', None)  # 当前登录用户
    now = time.strftime('%Y-%m-%d %H:%M:%S')    # 统一时间字符串格式
    row.status = 1                              # 1 = 已发布
    row.publish_user_id = getattr(user, 'id', None)  # 记录发布人；理论上已登录不会为 None
    row.publish_time = now                      # 记录发布时间
    row.save()                                  # 全字段保存（未提交字段保持原值）
    return ok(NoticeInfoSerializer(row).data, '发布成功')  # 返回最新对象，前端可即时更新
```

```python
    if not row:
        return fail('公告不存在', code=404)
    user = getattr(request, 'user_info', None)
    if not user or not getattr(user, 'id', None):
        return fail('未登录', code=401)          # 兜底登录校验
    now = time.strftime('%Y-%m-%d %H:%M:%S')     # 阅读时间与入库时间
    NoticeRead.objects.get_or_create(
        notice_id=pk,                            # 唯一条件一：公告 id
        user_id=user.id,                         # 唯一条件二：当前用户 id
        defaults={'read_time': now, 'create_time': now},
        # 不存在才插入；已存在则什么都不写，保证重复点击幂等
    )
    return ok(None, '已记录阅读')                 # 不返回阅读记录，减少响应体积
```

“幂等”的实现依赖 `get_or_create` 的「先查后插」；如果数据库没有 `(notice_id, user_id)` 唯一索引，并发下仍可能插两条（见问题清单）。

#### 视图业务逻辑

- 发布：
  - 校验公告存在且 `is_deleted=0`。
  - 直接把 `status` 置 1，不校验 `start_time/end_time`；即使开始时间在未来，也会返回「发布成功」，但门户的 `my` 接口仍会因 `start_time > now` 过滤掉它。
  - `row.save()` 是全字段保存，会把内存中读到的所有字段重新写回；没有更新 `update_by/update_time`（这两个字段本次不会被改）。
  - 权限：`publish` 不在 `perm_map`，只校验登录；前端按钮的 `notice:update` 只是展示层限制。
- 已读：
  - 校验公告存在、用户已登录。
  - `NoticeRead` 不继承 `BaseModel`，没有 `is_deleted`，所以查询/写入都不带逻辑删除条件。
  - 只写 `read_time/create_time`，不记录阅读 IP、来源等。
  - 权限：`read` 不在 `perm_map`，只校验登录。

## 07 模块小结

1. **消息模块（`apps/msg`）**
   - 路由挂在 `/api/msg/`，资源前缀 `template/record/push_log/push_config`。
   - `MsgTemplate`、`MsgRecord`、`MsgPushConfig` 继承 `BaseModel`，有审计字段和 `is_deleted` 逻辑删除。
   - `MsgPushLog` 不继承 `BaseModel`，没有 `is_deleted`，所以 `MsgPushLogViewSet` 重写了 `get_queryset()` 和 `list()`（`backend/apps/msg/views.py:89-100`），直接查全量。
   - 所有列表最终都走 `StandardPagination`，响应结构统一为 `data.{total,page,page_size,list}`。
2. **公告模块（`apps/notice`）**
   - 路由挂在 `/api/notice/`，资源前缀 `category/info/read`。
   - `NoticeCategory`、`NoticeInfo` 继承 `BaseModel`；`NoticeRead` 是纯流水表，不继承 `BaseModel`。
   - 后台管理列表走标准 `CrudViewSet.list()`；门户「我的可见公告」走自定义 `my`，会做状态、时间窗、角色范围三层过滤。
3. **共性**
   - 自定义动作（`my/read/read_all/publish/offline/status`）都没有登记到 `perm_map`，后端只校验登录，按钮权限只在前端 `v-perm` 生效。
   - 大整数主键由 `BigIntJSONRenderer` 统一转字符串，前端拿到的 `id` 可能是 string。

## 疑似问题（仅记录，未修改代码）

1. **单条已读存在越权**：`backend/apps/msg/views.py:58-59` 只按 `pk` 更新，没有校验 `receiver_id=当前用户`，任何登录用户可把他人消息标记为已读。
2. **自定义动作绕过按钮权限**：`perm_map` 只有 `list/create/update/delete`，`my/read/read_all/status/publish/offline` 都只校验登录；前端 `v-perm` 无法防止直接构造请求。
3. **消息模板状态语义不一致**：`backend/apps/msg/models.py:18` 注释为 `0 正常 / 1 停用`，前端 `frontend/src/views/msg/template/index.vue:55-58` 与 `104` 行按 `1 启用 / 0 停用` 使用。
4. **公告分类排序不稳定**：`backend/apps/notice/views.py:27` 设置 `order_by='sort'`，覆盖了模型 `Meta.ordering=['sort','id']`，`sort` 相同时没有二级排序。
5. **后台公告列表置顶不生效**：`backend/apps/notice/views.py:42` 的 `order_by='-id'` 覆盖了模型 `Meta.ordering=['-is_top','-id']`。
6. **公告分类名称缺失**：前端 `frontend/src/views/notice/info/index.vue:69` 期待 `row.category_name`，但 `NoticeInfoSerializer` 只输出 `notice_info` 自身字段，没有关联 `notice_category`。
7. **`role_scope` 约定冲突**：模型注释与 `my` 实现要求 JSON 数组（角色编码），前端表单提示却是「role_id 列表，逗号分隔」（`frontend/src/views/notice/info/index.vue:155-158`）。`json.loads('1,2')` 失败后 `scope_list=[]`，`backend/apps/notice/views.py:70-72` 会把它当成“全部可见”，存在可见范围被放大的风险。
8. **`user.roles` 不可用**：`backend/apps/notice/views.py:58-59` 读取 `user.roles`，但 `SysUser` 模型没有该属性（角色只在 `UserSerializer` 里以 `SerializerMethodField` 输出），导致 `role_list` 恒为空，带角色范围的公告对所有人都不可见。
9. **阅读记录并发重复**：`get_or_create` 依赖「先查后插」，`notice_read` 若无 `(notice_id,user_id)` 唯一索引，并发下可能插入重复记录。
10. **消息推送日志重复路由**：`backend/apps/msg/urls.py:34-35` 在 `crud()` 已生成 `push_log/list` 后又在 `extras` 里重复声明 `'list'`，Django 会保留两条相同 path（先匹配到第一条，功能不受影响，但属于冗余配置）。
11. **前端无入口的后端能力**：`/msg/record/my`、`/msg/record/read_all`、`/notice/info/my`、`/notice/info/read` 在 `frontend/src` 中没有调用点，目前只能通过接口直接访问。
