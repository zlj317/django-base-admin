# 03 系统管理：字典、参数配置与审计日志

> 覆盖示例 20-25。本篇的重点不是 CRUD 本身，而是三件“平台能力”：
> 1. 字典如何一次加载、全站复用；
> 2. 操作日志如何由中间件自动落库（而不是每个视图手写）；
> 3. 登录日志如何与认证流程绑定。

## 示例 20：字典类型分页列表

### 前端触发

[system/dict/index.vue](file:///d:/other/django-base-admin/frontend/src/views/system/dict/index.vue#L256-L272) 的 `fetchTypes()`，页面挂载时调用：

```js
// 拉取字典类型列表：分页参数与查询条件一起提交；失败时由请求拦截器统一提示
async function fetchTypes() {
  typeLoading.value = true  // 请求前开遮罩
  try {
    // GET /system/dict/type/list：dict_name/dict_type 均为模糊查询
    const res = await request.get('/system/dict/type/list', {
      params: { page: typePage.value, page_size: typePageSize.value, ...typeQuery }
    })
    // 后端约定 data = { list, total }
    typeList.value = res.data.list || []
    typeTotal.value = res.data.total || 0
    // 当前打开的字典类型可能已被删除，需要同步关闭右侧抽屉
    if (currentType.value && !typeList.value.some(t => t.id === currentType.value.id)) {
      closeDataDrawer()
    }
  } finally {
    typeLoading.value = false  // 成功失败都收起遮罩
  }
}
```

### 后端链路

`GET /api/system/dict/type/list` → [system/urls.py](file:///d:/other/django-base-admin/backend/apps/system/urls.py#L36) → `DictTypeViewSet.list`（基类实现）。

```python
class DictTypeViewSet(CrudViewSet):
    """字典类型管理视图：删除类型时级联删除其字典项。"""
    model = SysDictType  # 目标模型
    serializer_class = DictTypeSerializer
    perm_prefix = 'system:dict'  # 权限前缀，列表需要 system:dict:list
    module_name = '字典管理'  # 操作日志模块名
    filter_map = {'dict_name': 'icontains', 'dict_type': 'icontains'}  # 两个字段都做模糊匹配
```

基类 `list` 的执行顺序：

```python
queryset = self.apply_filters(self.get_queryset(), request)  # 先过滤，保证 total 准确
return StandardPagination(request).paginate(queryset, self.get_serializer_class())
```

最终 SQL 近似：`SELECT ... FROM sys_dict_type WHERE is_deleted=0 AND dict_name LIKE '%x%' ORDER BY id LIMIT 10 OFFSET 0`。

### 数据表

`sys_dict_type`：`id`、`dict_name`、`dict_type`（唯一编码）、`status`、`remark`、审计字段、`is_deleted`。

### Java 对照

`filter_map` ≈ 查询 DTO 字段 → `QueryWrapper.like`；`StandardPagination` ≈ `PageHelper`。

## 示例 21：全量启用字典项缓存

### 前端触发

登录后路由守卫会调用 `loadDicts()`（[router/index.js](file:///d:/other/django-base-admin/frontend/src/router/index.js)），请求 `/system/dict/data/all`，把结果缓存到本地，页面里通过字典工具做“值 → 标签”翻译。字典页的抽屉列表则用 `fetchData()`（[dict/index.vue](file:///d:/other/django-base-admin/frontend/src/views/system/dict/index.vue#L393-L405)）按类型编码查询：

```js
async function fetchData() {
  if (!currentType.value) return  // 抽屉未打开时不请求
  dataLoading.value = true
  try {
    // 用 dict_type 编码（不是类型 id）过滤，前端只持有编码
    const res = await request.get('/system/dict/data/list', {
      params: { page: dataPage.value, page_size: dataPageSize.value, dict_type: currentType.value.dict_type }
    })
    dataList.value = res.data.list || []
    dataTotal.value = res.data.total || 0
  } finally {
    dataLoading.value = false
  }
}
```

### 后端链路

- 全量：`GET /api/system/dict/data/all` → [DictDataViewSet.all](file:///d:/other/django-base-admin/backend/apps/system/views/dict.py#L46-L55)。
- 按编码分页：`GET /api/system/dict/data/list?dict_type=xxx` → [DictDataViewSet.get_queryset](file:///d:/other/django-base-admin/backend/apps/system/views/dict.py#L36-L44)。

```python
def all(self, request):
    """全部启用字典（前端缓存做翻译与下拉）。"""
    types = SysDictType.objects.filter(is_deleted=0, status=0)  # 启用的字典类型
    data = []
    for t in types:  # 逐类型查询启用字典项
        items = SysDictData.objects.filter(dict_type_id=t.id, is_deleted=0, status=0)
        data.append({'dict_type': t.dict_type,  # 类型编码作为前端缓存的键
                     'list': [{'dict_label': i.dict_label, 'dict_value': i.dict_value}
                              for i in items]})  # 只输出标签与键值
    return ok(data)
```

按编码过滤时做了一次“编码 → 主键”的换算：

```python
dict_type = self.request.query_params.get('dict_type')  # 类型编码
if dict_type:
    type_id = SysDictType.objects.filter(dict_type=dict_type, is_deleted=0) \
        .values_list('id', flat=True).first()  # 编码换算为主键
    qs = qs.filter(dict_type_id=type_id) if type_id else qs.none()  # 无匹配返回空集
```

`qs.none()` 生成 `WHERE 1=0`，比返回 `None` 更安全，后续分页/序列化都不会报错。

### 数据表

- `sys_dict_type`：类型编码与启用状态。
- `sys_dict_data`：`dict_type_id` 逻辑外键、`dict_label`、`dict_value`、`dict_sort`、`status`。

### 响应与消费

```json
{ "code": 200, "data": [
  { "dict_type": "sys_user_sex", "list": [{ "dict_label": "男", "dict_value": "0" }, { "dict_label": "女", "dict_value": "1" }] }
] }
```

前端把 `dict_type` 作为缓存 key，后续表格列渲染时用 `dict_value` 找到 `dict_label`，避免每个单元格都发请求。

### Java 对照

`all` ≈ 一次性预热到 Redis/本地缓存；N 次查询 ≈ 可优化为一次 `IN` 查询 + 内存分组，但当前字典量小，简单实现足够。

### 前端触发

[system/config/index.vue](file:///d:/other/django-base-admin/frontend/src/views/system/config/index.vue#L224-L250) 的 `handleSave()`：

```js
async function handleSave() {
  await formRef.value.validate()  // 名称/键名/键值必填
  saving.value = true
  try {
    const payload = {
      config_key: form.config_key,

  } finally {

  }

```

### 后端链路

`POST /api/system/config/create` → [ConfigViewSet](file:///d:/other/django-base-admin/backend/apps/system/views/config.py#L7-L13)，无自定义 create，走基类。

```python
class ConfigViewSet(CrudViewSet):
    """参数配置视图：仅需声明模型与筛选条件，CRUD 由基类提供。"""
    model = SysConfig
    serializer_class = ConfigSerializer
    perm_prefix = 'system:config'  # 需要 system:config:create
    module_name = '参数配置'
    filter_map = {'config_name': 'icontains', 'config_key': 'icontains'}
```

基类在落库前会遍历模型唯一字段，先查“未删除同名”再查“已删除同名”：

```python
qs = self.model.objects.filter(**{field.attname: value})  # 包含逻辑删除记录
if qs.filter(is_deleted=0).exists():
    return fail(f'{field.verbose_name}已存在', code=400)
if qs.exists():  # 只剩已删除记录占用数据库唯一键
    return fail(f'{field.verbose_name}已被已删除记录占用，请更换{field.verbose_name}', code=400)
```

`ConfigSerializer.validate_config_key` 再校验一次未删除记录唯一，形成“双保险”：基类负责给出明确 400，序列化器负责字段级错误。

### 数据表

`sys_config`：`config_key`（唯一）、`config_value`、`config_name`、`remark`，以及 `create_by/create_time/update_by/update_time/is_deleted`。

### Java 对照

唯一预校验 ≈ `existsByConfigKeyAndDeletedFalse`；`fail(..., code=400)` ≈ 抛业务异常由全局异常处理器转 `Result.fail`。

### 前端触发

[system/operlog/index.vue](file:///d:/other/django-base-admin/frontend/src/views/system/operlog/index.vue#L141-L153) 的 `fetchList()`，清空按钮调用 [handleClear](file:///d:/other/django-base-admin/frontend/src/views/system/operlog/index.vue#L213-L218)：

```js
async function fetchList() {
  loading.value = true
  try {
    // 三个条件：操作人/模块名模糊，操作类型精确
    const res = await request.get('/system/operlog/list', {
      params: { page: page.value, page_size: pageSize.value, ...query }
```

### 后端链路

- 列表：`GET /api/system/operlog/list` → [OperLogViewSet](file:///d:/other/django-base-admin/backend/apps/system/views/logs.py#L8-L19)。
- 清空：`POST /api/system/operlog/clear` → `OperLogViewSet.clear`。

```python
class OperLogViewSet(CrudViewSet):
    """操作日志视图：支持筛选与一键清空（逻辑删除）。"""
    model = SysOperLog
    serializer_class = OperLogSerializer
    perm_prefix = 'system:operlog'
    module_name = '操作日志'
    filter_map = {'oper_user': 'icontains', 'module_name': 'icontains', 'oper_type': 'exact'}

    def clear(self, request):
        """清空全部操作日志（批量逻辑删除）。"""
        self.get_queryset().update(is_deleted=1)  # 一条 UPDATE 批量打标记
        return ok(None, '日志已清空')
```

### 日志是怎么写进去的：中间件

这是本篇最重要的机制。任何 `POST/PUT/DELETE` 且路径以 `/api/` 开头的请求，都会在响应返回后被 [OperLogMiddleware](file:///d:/other/django-base-admin/backend/common/middleware.py#L32-L98) 记录：

```python
class OperLogMiddleware:
    """记录写操作到 sys_oper_log。"""

    def __init__(self, get_response):
        """Django 中间件约定：保存下一层调用链。"""
        self.get_response = get_response

    def __call__(self, request):
        """请求前后打点，仅对写接口落库，异常不影响主业务流程。"""
        started = time.time()
        body = b''
        if request.method in ('POST', 'PUT', 'DELETE') and not request.path.startswith(SKIP_PATHS):
            try:
                body = request.body[:2000]  # 截断请求体，防止大字段撑爆日志表
            except Exception:
                body = b''  # 读取失败时降级为空
        response = self.get_response(request)  # 先执行业务视图
        if request.method in ('POST', 'PUT', 'DELETE') and request.path.startswith('/api/') \
                and not request.path.startswith(SKIP_PATHS):
            try:
                self.save_log(request, response, body, int((time.time() - started) * 1000))
            except Exception:
                logger.exception('记录操作日志失败: %s %s', request.method, request.path)
        return response
```

操作类型由 URL 关键字推断（[middleware.py](file:///d:/other/django-base-admin/backend/common/middleware.py#L10-L23)）：

```python
OPER_TYPE_MAP = [
    ('importTemplate', '导入'), ('importData', '导入'), ('import', '导入'),
    ('export', '导出'), ('create', '新增'), ('update', '编辑'),
    ('delete', '删除'), ('assign', '编辑'), ('reset_pwd', '编辑'), ('status', '编辑'),
]
SKIP_PATHS = ('/api/auth/login', '/api/auth/logout')  # 登录/登出不记日志
```

模块名不靠手写，而是从视图类属性读取：

```python
func = getattr(match, 'func', None)  # as_view 包装后的可调用对象
view_class = getattr(func, 'view_class', None) or getattr(func, 'cls', None)
if view_class is not None:
    module_name = getattr(view_class, 'module_name', '')  # 例如"用户管理"
```

因此每个 ViewSet 都声明了 `module_name`，日志模块列才能显示中文名。

### 数据表

`sys_oper_log`：`oper_user`、`module_name`、`oper_type`、`request_url`、`request_param`、`response_result`、`cost_time`、`oper_time`、`create_time`、`is_deleted`。

### Java 对照

`OperLogMiddleware` ≈ `OncePerRequestFilter` 或 AOP `@Around` 切面；`module_name` 从视图类读取 ≈ 从 HandlerMethod 的类注解读取模块名；`request.body[:2000]` ≈ 请求体截断防止日志膨胀。

### 日志写入位置

登录成功/失败都调用 [login_log](file:///d:/other/django-base-admin/backend/apps/system/views/auth.py#L48-L53)：

```python
def login_log(username, ip, status, msg, browser=''):
    """写入登录日志，字段截断以匹配表长度。"""
    SysLoginLog.objects.create(
        username=username, ip=ip, status=status,
        login_time=time.strftime('%Y-%m-%d %H:%M:%S'),
        browser=browser[:100], msg=msg[:255],  # 截断避免超长写入失败
    )
```

登录视图的三处调用：

```python
if not user or not check_password(password, user.password):
    login_log(username, ip, 1, '用户名或密码错误', browser)  # 1=失败
    return fail('用户名或密码错误')
if user.status:
    login_log(username, ip, 1, '账号已被禁用', browser)
    return fail('账号已被禁用，请联系管理员')
login_log(username, ip, 0, '登录成功', browser)  # 0=成功
```

### 数据表

`sys_login_log`：`username`、`ip`、`login_time`、`status`、`browser`、`msg`、`create_time`、`is_deleted`。

### Java 对照

`login_log(...)` ≈ `loginLogService.record(...)`；失败不阻断主流程（这里失败也会继续返回业务错误），生产环境建议加 try/catch 或异步落库。

## 示例 25：删除字典类型并级联删除字典项

### 前端触发

[system/dict/index.vue](file:///d:/other/django-base-admin/frontend/src/views/system/dict/index.vue#L350-L357) 的 `handleTypeDelete(row)`：

```js
async function handleTypeDelete(row) {
  await ElMessageBox.confirm(`确定删除字典类型「${row.dict_name}」吗？其下字典项将不可用。`, '提示', { type: 'warning' })
  // 批量删除接口，这里只传一条 id 也一样走通
  await request.delete('/system/dict/type/delete', { data: { ids: [row.id] } })
  ElMessage.success('删除成功')
  if (currentType.value && currentType.value.id === row.id) closeDataDrawer()  // 清掉抽屉里的失效数据
  fetchTypes()
}
```

### 后端链路

`DELETE /api/system/dict/type/delete` → [DictTypeViewSet.delete](file:///d:/other/django-base-admin/backend/apps/system/views/dict.py#L17-L25)：

```python
def delete(self, request):
    """删除字典类型时同步删除其字典项。"""
    ids = request.data.get('ids') or []  # 待删除类型ID
    if not ids:
        return ok(None, '请选择要删除的数据')  # 未选数据不报错
    self.get_queryset().filter(id__in=ids).update(is_deleted=1)  # 逻辑删除类型
    SysDictData.objects.filter(dict_type_id__in=ids).update(is_deleted=1)  # 级联逻辑删除字典项
    return ok(None, '删除成功')
```

两条 UPDATE 不是事务包裹的；如果第二条失败，会出现“类型已删、字典项残留”的不一致。生产环境建议：

```python
from django.db import transaction

with transaction.atomic():  # 等价于 Spring 的 @Transactional
    ...
```

当前实现没有使用 `transaction.atomic()`，属于可改进点（本篇只记录，不修改代码）。

### 数据表

- `sys_dict_type.is_deleted`
- `sys_dict_data.is_deleted`（通过 `dict_type_id IN (...)` 批量更新）

### Java 对照

级联删除 ≈ `dictTypeMapper.deleteBatchIds` + `dictDataMapper.deleteByTypeIds`；事务 ≈ `@Transactional(rollbackFor = Exception.class)`。

## 本篇小结

- 字典分“类型 + 项”两张表，项通过 `dict_type_id` 逻辑关联；全量接口只返回启用项。
- 操作日志不是业务代码手写，而是中间件统一记录；模块名来自 ViewSet 的 `module_name`。
- 登录日志在认证视图内显式写入，成功与失败都有记录。
- 清空日志是批量逻辑删除，不是物理删除；`is_deleted` 让历史仍可追溯。
- 字典级联删除目前没有事务包裹，这是一个可以改进的点。
