# backend/apps/kb/urls.py:7-20
def crud(prefix, viewset, extras=None):
    """按前缀生成 list/create/delete/update，extras 追加自定义动作。"""
    def _join(s): return f'{prefix}/{s}' if prefix else s        # 拼出 category/list 这样的相对路径
    list_view = viewset.as_view({'get': 'list', 'post': 'create', 'delete': 'delete'})  # 三个动作共用一条路径
    item_view = viewset.as_view({'put': 'update'})               # 主键路径只有 PUT
    patterns = [
        path(_join('list'), list_view),                          # GET /kb/category/list
        path(_join('create'), list_view),                        # POST /kb/category/create
        path(_join('delete'), list_view),                        # DELETE /kb/category/delete
        path(_join('update/<int:pk>'), item_view),               # PUT /kb/category/update/123
    ]
    for suffix, methods in (extras or {}).items():               # extras 形如 {'stats': {'get': 'stats'}}
        patterns.append(path(_join(suffix), viewset.as_view(methods)))
    return patterns

# backend/apps/kb/urls.py:23-25
urlpatterns = crud('category', views.KBCategoryViewSet) + crud('document', views.KBDocumentViewSet, {
    'stats': {'get': 'stats'},                                   # GET /kb/document/stats
}) + crud('favorite', views.KBFavoriteViewSet)

### 0.4 与工单模块相比，本模块的两个结构性差异

1. **`CalSchedule / KBCategory / KBDocument` 继承 `BaseModel`**（有 `create_by/create_time/update_by/update_time/is_deleted`），所以 `create` 会自动补审计字段、`delete` 是逻辑删除。
2. **`CalReminder / KBFavorite` 不继承 `BaseModel`**（只有 `create_time`），所以：
   - `get_queryset` 必须覆写，不能调用基类的 `filter(is_deleted=0)`；
   - `create` 的 `audit` 为空字典，`create_time` 依赖数据库 `DEFAULT CURRENT_TIMESTAMP`；
   - `delete` 走 `queryset.delete()`，是**物理删除**。

前端把列表按「开始日期」分桶（这是日历渲染的核心）：

```vue
<!-- frontend/src/views/cal/schedule/index.vue:371-391 -->
// 一次遍历完成分桶 + 颜色计算
function buildScheduleMap(list) {
  scheduleMap.clear()                                   // 先清空，避免改期/删除后残留旧索引
  ;(list || []).forEach(s => {
    // start_time 形如 'YYYY-MM-DD HH:mm:ss'，取前 10 位作为日期键
    const date = (s.start_time || '').slice(0, 10)
    if (!date) return                                   // 无开始时间的脏数据不分桶
    let color = 'blue'                                  // 默认蓝
    if (s.all_day) color = 'purple'                    // 全天 → 紫
    if (s.status === 0) color = 'gray'                 // 前端认为 status=0 是停用 → 灰（优先级最高）
    s.color = color                                     // 直接给对象补字段，模板用 ev.color
    if (!scheduleMap.has(date)) scheduleMap.set(date, [])
    scheduleMap.get(date).push(s)
  })
  // 同一天内按开始时间升序，保证事件顺序稳定
  scheduleMap.forEach(arr => arr.sort((a, b) => (a.start_time || '').localeCompare(b.start_time || '')))
}
```

`list` 仍然复用基类（`common/views.py:58-61`）：

```python
# backend/common/views.py:50-61
def apply_filters(self, queryset, request):
    for param, lookup in self.filter_map.items():       # 只遍历白名单里的 3 个键
        value = request.query_params.get(param)         # 取 ?title=...&owner_id=...
        if value not in (None, ''):                     # 空值视为不筛选
            queryset = queryset.filter(**{f'{param}__{lookup}': value})
    return queryset

def list(self, request):
    queryset = self.apply_filters(self.get_queryset(), request)
    return StandardPagination(request).paginate(queryset, self.get_serializer_class())
```

**这里有一个必须讲清楚的行为**：前端 401-402 行拼的 `start_time__gte` 和 `end_time__lte` **不在 `filter_map` 里**，`apply_filters` 只遍历 `{'title','owner_id','status'}`，所以这两个参数会被静默丢弃。结果是：

- 顶部「日期范围」控件对后端数据没有任何过滤作用；
- 后端仍会返回全部日程（最多 `page_size=500` 条）；
- 日历之所以看起来正常，是因为前端 `buildScheduleMap` 把所有数据按日期分桶，月视图只渲染当前月的格子，用户感知不到“没过滤”。

如果要在后端真正支持范围过滤，需要把参数声明成 `filter_map` 的两个键（`start_time__gte` 这种带 lookup 的键名不能直接当查询参数名），或在子类里覆写 `apply_filters`。

**数据表与 ORM/SQL**

模型（`backend/apps/cal/models.py:8-25`）：

```python
class CalSchedule(BaseModel):

```

DDL（`docs/new_features_init.sql:437-455`）关键点：只有 `PRIMARY KEY(id)` 和 `KEY idx_owner(owner_id)`，`start_time` **没有索引**。按时间范围查询在小数据量下无感，数据量大时 `WHERE start_time >= ?` 会走全表扫描。

本次请求等价 SQL：

```sql
SELECT *
FROM cal_schedule
WHERE is_deleted = 0
  AND title LIKE '%周会%'        -- 仅当传了 title
  AND owner_id = 1001            -- 仅当传了 owner_id
  AND status = 0                 -- 仅当传了 status
ORDER BY start_time DESC
LIMIT 500 OFFSET 0;
-- 注意：start_time >= ? / end_time <= ? 没有出现在 WHERE 里
```

`BigIntegerField` 的 `owner_id` 是逻辑外键：数据库没有 `FOREIGN KEY`，ORM 也不会 join 用户表，所以列表拿不到负责人姓名，前端只能用数字 id 或额外请求用户列表。

```python
# backend/common/views.py:63-92
def create(self, request):
    """新增接口：唯一性预检 → 序列化校验 → 补审计字段 → 落库 → 回写完整对象。"""
    for field in self.model._meta.fields:
        # CalSchedule 没有字段级 unique（主键除外），所以这个循环实际上什么都不做
        if not field.unique or field.primary_key or not hasattr(self.model, 'is_deleted'):
            continue
        value = request.data.get(field.attname)
        if value in (None, ''):
            continue
        qs = self.model.objects.filter(**{field.attname: value})
        if qs.filter(is_deleted=0).exists():
            return fail(f'{field.verbose_name}已存在', code=400)
        if qs.exists():
            return fail(f'{field.verbose_name}已被已删除记录占用，请更换{field.verbose_name}', code=400)

    # 关键：ModelSerializer 按模型字段类型做严格校验
    serializer = self.get_serializer_class()(data=request.data)
    serializer.is_valid(raise_exception=True)

    # CalSchedule 继承 BaseModel → hasattr(create_by) 为真，补 4 个审计字段
    now = time.strftime('%Y-%m-%d %H:%M:%S')
    user = getattr(request, 'user_info', None)
    audit = {}
    if hasattr(self.model, 'create_by'):
        audit = dict(create_by=user.username if user else '', create_time=now,
                     update_by=user.username if user else '', update_time=now)
    instance = serializer.save(**audit)            # 雪花 id 由字段默认值生成

    self.after_create(request, instance)           # 子类未覆写，空实现
    return ok(self.get_serializer_class()(instance).data, '新增成功')
```

**按 DRF 3.17 的实际字段约束，这个新建请求会命中两处校验错误**（字段约束已用项目 venv 打印确认）：

| 提交值 | 序列化器字段 | 校验结果 | 原因 |
| --- | --- | --- | --- |
| `all_day: false` | `IntegerField`（模型是 `SmallIntegerField`） | **400 invalid** | DRF `IntegerField.to_internal_value` 执行 `int(str(False))`，`int('False')` 抛 `ValueError` |
| `reminder_minutes: null` | `IntegerField(null=False)` | **400 “该字段不能为 null”** | 模型 `default=0` 且未设 `null=True`，序列化器 `allow_null=False` |

也就是说，用页面默认值（全天关闭、不提醒）提交，后端会直接返回 `code=400`。只有把「提前提醒」选一个具体分钟数、并避免传布尔型的 `all_day`（例如改成 1）才能通过。这是静态推断 + 框架源码确认的结论，建议实测一次 `POST /api/cal/schedule/create`。

另外两个业务语义问题：

1. **`status` 语义前后端相反**：模型注释 `0 正常 / 1 取消`（`models.py:20`），DDL 注释 `0正常 1取消`（`new_features_init.sql:448`），但前端把 `1` 当“启用”、`0` 当“停用”（`schedule/index.vue:255`），`buildScheduleMap` 又把 `status === 0` 涂成灰色（381 行）。新建默认 `status=1`，按模型语义其实是“已取消”，但界面显示“启用”、颜色是蓝色。

// 递归建树：parent_id 可能是 null / 0 / undefined，统一收敛成 null 再比较
function buildTree(list, parentId = null) {
  return list
    .filter(x => (x.parent_id || null) === parentId)   // 0 与 null 都视为根
    .sort((a, b) => (a.sort || 0) - (b.sort || 0))     // 同级按 sort 升序
    .map(x => ({ ...x, children: buildTree(list, x.id) }))  // 递归挂子级
}

1. `order_by='sort'` 只是 SQL 第一排序键；`KBCategory.Meta.ordering=['sort','id']` 会不会生效？——不会。显式 `order_by('sort')` 覆盖了 Meta 的默认排序，所以最终只有 `ORDER BY sort ASC`，`sort` 相同时顺序由数据库决定。前端 `buildTree` 会再按 `sort` 排一次，但 `sort` 相同节点的相对顺序同样不稳定。

```python
# backend/apps/kb/views.py:41-52
def stats(self, request):
    """文档列表顶部统计：总数、今日新增、已发布、累计阅读。"""
    queryset = KBDocument.objects.filter(is_deleted=0)      # 只统计未删除文档
    today = datetime.date.today().strftime('%Y-%m-%d')      # 服务器本地日期，字符串形式
    total_reads = queryset.aggregate(total=Sum('read_count'))['total'] or 0  # NULL 时兜底 0
    data = {
        'total_documents': queryset.count(),                 # COUNT(*)
        'today_new': queryset.filter(create_time__date=today).count(),  # DATE(create_time) = today
        'published': queryset.filter(status=1).count(),     # status=1 已发布
        'total_reads': total_reads,                          # SUM(read_count)
    }
    return ok(data)                                          # 直接返回 4 个键的对象
```

要点：

1. **没有 `@action` 装饰器**，但通过 `as_view({'get':'stats'})` 仍能正常工作；`stats` 的签名是 `(self, request)`，不能加 `pk`。
2. **4 次数据库查询**：`count()`、`count()`、`count()`、`aggregate(Sum)`，没有合并成一次。Java 里通常用一条 `SELECT COUNT(*), SUM(read_count), SUM(status=1) ...` 或分开缓存。
3. **`create_time__date` 依赖数据库时区**：Django 生成 `DATE(create_time)`，`USE_TZ=False` 下按本地时间比较，与前端“今天”的认知一致（同一台服务器）。
4. **统计 action 不在权限映射里**：`view.action='stats'`，`perm_map` 只有 `list/create/update/delete`，`PermissionCheck` 取不到 `required` 就放行（`common/permissions.py:53-55`），所以只要登录就能看统计。
5. **`published` 只认 `status=1`**，DDL 里还有 `status=2 下线`，下线文档既不算已发布，也没有单独卡片。

**数据表与 ORM/SQL**

表结构见示例 52。四条 SQL：

```sql
SELECT COUNT(*) FROM kb_document WHERE is_deleted = 0;

SELECT COUNT(*) FROM kb_document
WHERE is_deleted = 0 AND DATE(create_time) = '2026-11-06';

SELECT COUNT(*) FROM kb_document
WHERE is_deleted = 0 AND status = 1;

SELECT SUM(read_count) FROM kb_document WHERE is_deleted = 0;
```

`DATE(create_time)` 会让 `create_time` 上的索引（如果有）失效，因为列被函数包裹；数据量大时建议改成 `create_time >= 今天0点 AND create_time < 明天0点`。

| 无 `is_deleted` → 物理删除 | `repository.deleteById(id)` |
| 无审计字段 | 建议补 `createdBy`，便于排查谁收藏 |

## 模块小结

### 日历模块

| 能力 | 接口 | 实现要点 |
| --- | --- | --- |
| 日程列表 | `GET /cal/schedule/list` | `filter_map` 只有 title/owner_id/status；**日期范围参数被忽略** |
| 新建日程 | `POST /cal/schedule/create` | 基类 create；`all_day` 布尔、`reminder_minutes=null` 会触发 400 |
| 提醒列表 | `GET /cal/reminder/list` | 无 `is_deleted`，覆写 `get_queryset` |
| 提醒增删改 | `/cal/reminder/{create,update,delete}` | 删除是物理删除 |

### 知识库模块

| 能力 | 接口 | 实现要点 |
| --- | --- | --- |
| 分类树 | `GET /kb/category/list` | 后端返回平铺，前端 `buildTree` 递归建树 |
| 分类增删改 | `/kb/category/{create,update,delete}` | 根级新建传 `parent_id=null` 会被序列化器拒绝；删除不级联 |
| 文档列表 | `GET /kb/document/list` | 4 个筛选键；无 category_name/author_name |
| 文档统计 | `GET /kb/document/stats` | 4 次查询；`create_time__date` 包函数 |
| 收藏 | `/kb/favorite/*` | 无前端页面；联合唯一键未被 create 预检识别 |

### 与 Java 项目的落地对照

1. **Serializer ≈ DTO + 校验 + Jackson**：`fields='__all__'` 等价于直接暴露实体，缺少 VO 裁剪，容易把 `is_deleted` 等内部字段吐给前端。
2. **ViewSet ≈ Controller**：一个类承载 list/create/update/delete，子类只做配置，等价于 `BaseController` + 配置式 `QueryWrapper`。
3. **Model ≈ Entity + Repository**：`managed=False` 表示表结构不在 ORM 里维护，等价于 JPA `ddl-auto=none` + Flyway/SQL 脚本。
4. **`crud()` ≈ 批量 `@RequestMapping`**：`/create`、`/list` 是动作式 URL，不是 REST 资源式 URL。
5. **`PermissionCheck` ≈ 拦截器**：按 `view.action` 去 `perm_map` 取权限标识，未声明就只校验登录。
6. **`StandardPagination` ≈ PageHelper**：`{total,page,page_size,list}`。
7. **事务**：本模块所有写操作都是单表单条 `save()`，没有跨表事务需求；但注意 `create` 的“预检 + 插入”不是原子操作，并发下仍可能撞唯一键。

## 疑似问题（静态阅读结论，建议实测确认）

1. **日程日期范围筛选失效**：`frontend/src/views/cal/schedule/index.vue:401-402` 传 `start_time__gte/end_time__lte`，但 `ScheduleViewSet.filter_map`（`backend/apps/cal/views.py:13-17`）只有 `title/owner_id/status`，`apply_filters` 会静默丢弃这两个参数，顶部日期范围控件没有任何效果。
2. **新建日程默认值必然 400**：`form_orig.all_day=false`（`schedule/index.vue:326`）提交给 `IntegerField`，DRF `int('False')` 抛 `invalid`；`reminder_minutes=null`（同处）提交给 `allow_null=False` 的 `IntegerField`，报“不能为 null”。不选「提前提醒」+ 全天关闭时无法创建。
3. **日程 `status` 语义前后端相反**：模型/DDL 是 `0 正常 / 1 取消`（`models.py:20`、SQL 448 行），前端把 `1` 当“启用”、`0` 当“停用”，且 `buildScheduleMap` 把 `status===0` 涂灰（`schedule/index.vue:381`）。新建默认 `status=1`，按模型语义等于“已取消”，界面却显示“启用”。
4. **日程起止时间无交叉校验**：前端注释称“由后端校验”（`schedule/index.vue:231`），后端 `create/update` 没有任何比较逻辑，`end_time < start_time` 可以入库。
5. **提醒状态 2 的含义三处不一致**：模型 `2 已忽略`（`models.py:34`）、DDL `2失败`（SQL 463 行）、前端 `2 已忽略`（`reminder/index.vue:183`）。
6. **根级分类新建会 400**：`openCreate(null)` 提交 `parent_id: null`（`category/index.vue:336`），而 `parent_id` 的序列化字段 `allow_null=False`（模型 `default=0`、无 `null=True`），显式 null 被拒绝。
7. **分类删除不级联**：前端确认文案写“子分类将一并删除”（`category/index.vue:378`），基类 `delete` 只更新选中行（`common/views.py:118-121`），子分类会变成孤儿（`parent_id` 指向已删除节点）。
8. **分类列表排序不稳定**：`order_by='sort'` 覆盖了 `Meta.ordering=['sort','id']`，`sort` 相同的节点顺序由数据库决定，前端再排序也只在同一批数据内生效。
9. **新建文档默认值会 400**：`form.version='1.0'`（字符串，`document/index.vue:309`）提交给 `IntegerField`；`form.file_id=''`（空串，同处）提交给 `BigIntegerField`。两者都不满足 DRF 默认校验，按页面默认值新增文档会失败（版本历史因此也从未真正使用）。
10. **文档列表缺关联名称**：序列化器 `fields='__all__'` 只返回 `category_id/author_id`，前端却优先读 `category_name/author_name`（`document/index.vue:127` 等），作者列最终显示数字 ID。
11. **热门标签是假数据**：`hotTags` 写死在前端（`document/index.vue:336-345`），`count` 与 `kb_document.tags` 毫无关系，也没有任何后端聚合接口。
12. **阅读数不会增长**：列表只展示 `read_count`，`handleRead`（`document/index.vue:423-426`）只打开抽屉，没有调用任何累加接口，阅读数将永远是种子值。
13. **统计接口权限缺口 + 性能**：`stats` 不在 `perm_map`（`PermissionCheck` 只校验登录）；内部连打 4 次查询，且 `create_time__date` 会让日期列索引失效。
14. **收藏接口无前端入口**：`frontend/src/views/kb` 只有 category/document 两个页面，全仓库无 `favorite` 调用；接口存在但无人使用。
15. **重复收藏会 500**：`kb_favorite` 有联合唯一 `uk_doc_user`，但基类 `create` 只检查字段级 `unique=True`（`common/views.py:66-68`），重复插入触发 `IntegrityError`，没有友好提示。
16. **收藏/提醒物理删除且无审计**：两张表都不继承 `BaseModel`，删除不可恢复、无法追溯操作人；`doc_id`/`user_id`/`schedule_id` 无外键，源数据删除后留下悬挂引用。
17. **`kb_document.status` 的 2（下线）无 UI 支持**：DDL 注释有 `2下线`，模型只有 0/1，前端只渲染“发布/草稿”，统计的 `published` 也只统计 1。
