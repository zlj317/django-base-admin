### 0.4 只讲一次的通用基类

工单三个 ViewSet 都继承 `CrudViewSet`，列表/新增/编辑/删除的主干逻辑全部在基类里。
先读懂下面这段代码，后面的示例只需要看「子类声明了什么」和「自定义动作做了什么」。

```python
# backend/common/views.py:11-61
class CrudViewSet(viewsets.ViewSet):
    """通用 CRUD。子类只声明 model / serializer_class / perm_prefix / filter_map / order_by / module_name。"""

    model = None            # 子类必须指定模型类，例如 WorkOrder
    serializer_class = None # 子类必须指定序列化器，例如 WorkOrderSerializer
    perm_prefix = ''        # 权限前缀，例如 'wo'，会拼成 wo:list / wo:create / ...
    filter_map = {}         # 查询参数 → ORM lookup 的白名单映射
    order_by = 'id'         # 默认排序，保证分页切片结果稳定
    module_name = ''        # 操作日志模块名（当前版本给前端/日志预留）

    @property
    def permission_classes(self):
        """DRF 在进入视图前读取该属性；这里把它做成动态生成权限映射的入口。"""
        prefix = self.perm_prefix                                  # 取子类声明的权限前缀
        self.perm_map = {
            'list': f'{prefix}:list',                              # 列表权限标识
            'create': f'{prefix}:create',                          # 新增权限标识
            'update': f'{prefix}:update',                          # 编辑权限标识
            'delete': f'{prefix}:delete',                          # 删除权限标识
        }
        return [PermissionCheck]                                   # 登录校验已包含在 PermissionCheck 内部

    def get_queryset(self):
        """所有业务表统一过滤逻辑删除；日志类模型会在子类里覆写本方法。"""
        return self.model.objects.filter(is_deleted=0).order_by(self.order_by)

    def get_serializer_class(self):
        """返回类属性上的序列化器，子类无需再实现方法。"""
        return self.serializer_class

    def apply_filters(self, queryset, request):
        """只把 filter_map 里声明过的参数拼进 WHERE，未声明的参数会被静默忽略。"""
        for param, lookup in self.filter_map.items():
            value = request.query_params.get(param)                # 取 URL 查询串中的值
            if value not in (None, ''):                            # 空串/null 代表“不筛选”
                queryset = queryset.filter(**{f'{param}__{lookup}': value})
        return queryset

    def list(self, request):
        """列表接口：先过滤再分页，保证 total 与当前条件一致。"""
        queryset = self.apply_filters(self.get_queryset(), request)
        return StandardPagination(request).paginate(queryset, self.get_serializer_class())
```

分页器的实现（`total` 先 count、再切片，不会把全表加载进内存）：

```python
# backend/common/pagination.py:12-37
try:
    self.page = max(int(request.query_params.get('page', 1)), 1)      # 页码最小 1，避免负偏移
except (TypeError, ValueError):
    self.page = 1                                                      # 非数字回退第一页

try:
    self.page_size = int(request.query_params.get('page_size', settings.PAGE_DEFAULT_SIZE))
except (TypeError, ValueError):
    self.page_size = settings.PAGE_DEFAULT_SIZE                        # 非法值回退配置默认值（10）
self.page_size = min(max(self.page_size, 1), 1000)                     # 强制限制 1~1000，防止拉全表

@property
def offset(self):
    return (self.page - 1) * self.page_size                            # SQL OFFSET

def paginate(self, queryset, serializer_class=None, many=True):
    total = queryset.count()                                           # 先算总数
    rows = queryset[self.offset:self.offset + self.page_size]          # ORM 切片 = LIMIT/OFFSET
    data = {
        'total': total,
        'page': self.page,
        'page_size': self.page_size,
        'list': serializer_class(rows, many=many).data if serializer_class else list(rows),
    }
    return ok(data)                                                    # 包成 {code,msg,data}
```

统一响应与雪花 ID 精度处理：

```python
# backend/common/response.py:5-31
MAX_SAFE_INTEGER = 2 ** 53 - 1        # JavaScript Number 能精确表示的最大整数

def stringify_big_int(value):
    """递归把大整数转字符串，避免前端把 1943... 这样的雪花 ID 舍入成别的数。"""
    if isinstance(value, bool):
        return value                  # bool 是 int 子类，必须先排除，否则 True 会变成 'True'
    if isinstance(value, int):
        return str(value) if abs(value) > MAX_SAFE_INTEGER else value
    if isinstance(value, dict):
        return {key: stringify_big_int(item) for key, item in value.items()}
    if isinstance(value, (list, tuple)):
        return [stringify_big_int(item) for item in value]
    return value

def ok(data=None, msg='success'):
    return Response({'code': 200, 'msg': msg, 'data': data})   # HTTP 状态恒为 200，业务码放在 body

def fail(msg='error', code=500, data=None):
    return Response({'code': code, 'msg': msg, 'data': data})  # 404/400 也是 HTTP 200
```

Java 等价物：`ok/fail` ≈ `Result<T>` 静态工厂；`stringify_big_int` ≈ Jackson 的 `@JsonSerialize(using = ToStringSerializer.class)`。

路由生成器（三个模块的 `urls.py` 都是同一份模板）：

```python
# backend/apps/wo/urls.py:7-20
def crud(prefix, viewset, extras=None):
    """给一个前缀批量生成 list/create/delete/update 路由，extras 用于追加自定义动作。"""
    def _join(s): return f'{prefix}/{s}' if prefix else s          # 前缀为空时不产生多余的 '/'
    # 同一个 as_view 映射被三个 URL 复用：GET=列表、POST=新增、DELETE=删除
    list_view = viewset.as_view({'get': 'list', 'post': 'create', 'delete': 'delete'})
    item_view = viewset.as_view({'put': 'update'})                 # 主键路径只开放 PUT（没有 GET 详情）
    patterns = [
        path(_join('list'), list_view),                            # /wo/type/list
        path(_join('create'), list_view),                          # /wo/type/create
        path(_join('delete'), list_view),                          # /wo/type/delete
        path(_join('update/<int:pk>'), item_view),                 # /wo/type/update/123
    ]
    for suffix, methods in (extras or {}).items():                 # 工单列表用它挂 assign/solve/close
        patterns.append(path(_join(suffix), viewset.as_view(methods)))
    return patterns
```

> 注意一个与 Spring 习惯不同的点：`/type/create` 这条路径不仅接受 POST，还接受 GET(list) 和 DELETE(delete)；`/type/list` 同样接受 DELETE。这是“动作式 URL + 共享 as_view”带来的路由重叠，不是标准 REST。Java 里通常用 `@PostMapping("/create")` 精确限定。

权限是按 action 动态计算的（`common/views.py:30-40`）：`permission_classes` 被 DRF 读取时，先把 `perm_map` 挂到视图实例上，再返回 `PermissionCheck`。`PermissionCheck.has_permission`（`common/permissions.py:46-59`）用 `view.action` 查映射，查不到就直接放行（只要求登录）。校验流程是：

```python
# backend/common/permissions.py:46-59（节选）
def has_permission(self, request, view):
    if not super().has_permission(request, view):
        return False                                          # 登录校验失败（内部已抛 401）
    perm_map = getattr(view, 'perm_map', None)
    if not perm_map:
        return True                                           # 没有声明映射 = 不做按钮级鉴权
    required = perm_map.get(view.action)                      # 例如 action='list' → 'wo:list'
    if not required:
        return True                                           # 当前 action 没配权限 → 放行
    perms = get_user_perms(request.user_info)                 # 查用户-角色-菜单得到的权限集合
    if '*:*:*' in perms or required in perms:
        return True                                           # 超管通配或已授权
    raise drf_exceptions.PermissionDenied(f'没有操作权限：{required}')
```

列表的实际执行顺序：

```python
# backend/common/views.py:42-61
def get_queryset(self):
    return self.model.objects.filter(is_deleted=0).order_by(self.order_by)   # 逻辑删除过滤 + 排序

def apply_filters(self, queryset, request):
    for param, lookup in self.filter_map.items():                            # 只认白名单参数
        value = request.query_params.get(param)                              # 取 ?type_name=网络
        if value not in (None, ''):                                          # 空串/null 跳过
            queryset = queryset.filter(**{f'{param}__{lookup}': value})      # type_name__icontains='网络'
    return queryset

def list(self, request):
    queryset = self.apply_filters(self.get_queryset(), request)              # 先过滤
    return StandardPagination(request).paginate(queryset, self.get_serializer_class())
```

`icontains` 是 Django ORM 的 lookup，等价于 SQL 的 `LIKE '%值%'`（MySQL 默认不区分大小写）；`exact` 等价于 `=`。这些 lookup 是以字符串拼进 `filter(**{...})` 的，属于“白名单内的动态 SQL”，参数值仍由 ORM 转义，不存在拼接注入。

**Java 对照**

| Django/DRF 概念 | Spring 对应物 | 差异要点 |
| --- | --- | --- |
| `ModelSerializer` | DTO + Jackson + Bean Validation | 一个类同时负责入参校验和出参序列化 |
| `ViewSet` + `as_view({'get':'list'})` | `@RestController` 的方法映射 | DRF 把 HTTP 方法映射到 action 名 |
| `CrudViewSet` | 抽象 `BaseController`/`BaseService` | 配置式继承，子类几乎不写代码 |
| `filter_map` + `apply_filters` | `QueryWrapper` 动态拼接 | lookup 后缀（`icontains`）代替 `like()` |
| `PermissionCheck` | `HandlerInterceptor` / Spring Security | 权限标识按 `action` 动态取 |

# backend/common/views.py:63-92
def create(self, request):
    """新增接口：校验入参后补审计字段并回写完整对象。"""
    # 1) 唯一性预检：只处理“字段级 unique”字段，避免落库时撞唯一索引直接 500
    for field in self.model._meta.fields:
        if not field.unique or field.primary_key or not hasattr(self.model, 'is_deleted'):
            continue                                   # 主键、非唯一字段、日志类模型都跳过
        value = request.data.get(field.attname)        # 取前端提交的唯一字段值
        if value in (None, ''):
            continue                                   # 没传就交给序列化器
        qs = self.model.objects.filter(**{field.attname: value})   # 含已删除记录
        if qs.filter(is_deleted=0).exists():
            return fail(f'{field.verbose_name}已存在', code=400)
        if qs.exists():
            return fail(f'{field.verbose_name}已被已删除记录占用，请更换{field.verbose_name}', code=400)

    # 2) 反序列化校验：ModelSerializer 会按模型字段类型/长度/非空做校验
    serializer = self.get_serializer_class()(data=request.data)
    serializer.is_valid(raise_exception=True)          # 失败由全局异常处理器转 HTTP 200 + code=400

    # 3) 补审计字段：只有继承 BaseModel 的模型才有这四列
    now = time.strftime('%Y-%m-%d %H:%M:%S')            # 统一 'YYYY-MM-DD HH:MM:SS' 字符串
    user = getattr(request, 'user_info', None)          # JWT 认证后挂在 request 上的当前用户
    audit = {}
    if hasattr(self.model, 'create_by'):
        audit = dict(
            create_by=user.username if user else '',    # 创建人账号
            create_time=now,
            update_by=user.username if user else '',    # 初始更新人 = 创建人
            update_time=now,
        )
    instance = serializer.save(**audit)                 # 落库；雪花主键由字段 default=next_id 生成

    # 4) 扩展钩子 + 统一响应
    self.after_create(request, instance)                # 工单模块没有覆写，空实现
    return ok(self.get_serializer_class()(instance).data, '新增成功')
```

本模块的特殊点：

- `WorkOrder` 没有任何字段级 `unique=True`，所以第 1 步的循环实际不产生校验；`order_no` 虽然有业务唯一意味，但模型/DDL 都没有唯一索引。
- `order_no` **不会自动生成**。模型注释写着“自动生成的编号”，但 `WorkOrderViewSet` 没有覆写 `create`/`after_create`，全仓库也没有为工单写编号的代码（`order_no` 只在种子数据里出现）。新建后的工单 `order_no` 为 `NULL`，列表里「工单号」列会是空白。
- `creator_id` **不会自动填当前登录人**，前端弹窗里是手填数字输入框（`order/index.vue:187-194`）。这是与常见工单系统最大的差异。
- 没有事务、没有写 `work_order_log` 的 create 日志（对比示例 45-47，只有流转动作才写日志）。

# backend/apps/wo/views.py:53-70
@action(detail=True, methods=['put'])          # 装饰器语义：详情型动作、只接受 PUT；本项目用手写路由，装饰器主要起标记作用
def assign(self, request, pk=None):
    """指派处理人：assignee_id + 写 assign 日志。"""
    # 1) 查工单：逻辑删除的记录视为不存在
    row = WorkOrder.objects.filter(pk=pk, is_deleted=0).first()
    if not row:
        return fail('工单不存在', code=404)      # HTTP 仍是 200，业务码 404

    # 2) 取当前登录人与目标处理人
    user = getattr(request, 'user_info', None)   # JWT 认证后挂在 request 上；未登录时 None
    assignee_id = request.data.get('assignee_id')
    if assignee_id is None:
        return fail('请指定处理人', code=400)    # 只判“有没有传”，不校验用户是否存在

    # 3) 更新主表：这里只改处理人，不改 status
    now = time.strftime('%Y-%m-%d %H:%M:%S')     # USE_TZ=False，直接存本地时间的字符串
    row.assignee_id = assignee_id                # BigIntegerField，前端传数字或数字字符串都可
    row.update_by = user.username if user else ''
    row.update_time = now
    row.save()                                   # 只保存本行；没有事务包裹

    # 4) 写流转日志：work_order_log 是独立表，第二次 INSERT
    self._write_log(pk, getattr(user, 'id', None), 'assign',
                    f'指派给用户ID {assignee_id}')

    # 5) 回传最新工单完整对象
    return ok(WorkOrderSerializer(row).data, '指派成功')
```

日志写入的私有方法：

```python
# backend/apps/wo/views.py:43-51
def _write_log(self, order_id, operator_id, action, comment=''):
    """内部方法：向 work_order_log 插入一条日志。"""
    WorkOrderLog.objects.create(
        order_id=order_id,                        # 逻辑外键 → work_order.id
        operator_id=operator_id,                  # 当前登录用户 id；未登录为 None
        action=action,                            # 'assign' / 'solve' / 'close'
        comment=comment,                          # 人类可读的说明
        create_time=time.strftime('%Y-%m-%d %H:%M:%S'),  # 日志表没有 BaseModel 的审计列，手工写时间
    )
```

必须知道的三个行为：

1. **没有事务**。`row.save()` 成功、`_write_log` 失败时，主表已改但日志缺失。Java 里这段通常放在 `@Transactional` 方法中。

@action(detail=True, methods=['put'])
def solve(self, request, pk=None):
    """标记已解决：status=2 + 写 solve 日志。"""
    # 1) 只查未删除工单
    row = WorkOrder.objects.filter(pk=pk, is_deleted=0).first()
    if not row:
        return fail('工单不存在', code=404)

    # 2) 当前登录人（用于审计字段与日志）
    user = getattr(request, 'user_info', None)

    # 3) 直接改状态为 2（已解决），不校验原状态
    now = time.strftime('%Y-%m-%d %H:%M:%S')
    row.status = 2                                    # 0 待处理 / 1 处理中 / 2 已解决 / 3 已关闭
    row.update_by = user.username if user else ''
    row.update_time = now

## 模块小结

### 工单状态机（代码实际行为）

```text
新建(status=0 待处理)
   │
   ├── 指派 assign ────────────► status 仍是 0（不会变成 1）
   ├── 编辑 update ────────────► 可任意写 status（唯一能把 status 改成 1 的入口）
   ├── 解决 solve ─────────────► status = 2（不检查原状态）
   └── 关闭 close ─────────────► status = 3，写 close_time（不检查原状态）
```

### 本模块的四个“配置点”

| 配置 | 作用 | 位置 |
| --- | --- | --- |
| `perm_prefix` | 生成 `wo:list/create/update/delete` | 各 ViewSet 类属性 |
| `filter_map` | 声明允许的查询参数与 lookup | 各 ViewSet 类属性 |
| `order_by` | 分页前的稳定排序 | 各 ViewSet 类属性 |
| `module_name` | 操作日志模块名（当前仅声明） | 各 ViewSet 类属性 |

### 与 Java 项目落地时的对照清单

1. **路由不是 RESTful**：`/create`、`/list`、`/delete` 是动作式 URL；一个 `as_view` 复用到多条路径，导致方法重叠。
2. **没有详情接口**：`update/<pk>` 只支持 PUT，前端“详情”直接用列表行数据 + 日志接口。
3. **逻辑删除**：业务表 `is_deleted=1`，日志/收藏/提醒类表没有该列，直接物理删除。
4. **雪花 ID 字符串化**：JS 侧 id 是字符串，不要 `parseInt` 后再回传。
5. **审计字段由后端覆盖**：`create_by/create_time/update_by/update_time` 不接受前端伪造。
6. **自定义动作绕过细粒度权限**：`assign/solve/close` 只要求登录。

## 疑似问题（静态阅读结论，建议实测确认）

1. **`status=1`（处理中）在 UI 上不可达**：`WorkOrderViewSet.assign`（`views.py:53-70`）只改 `assignee_id`，不改 `status`；新建默认 0；编辑弹窗没有状态控件。而「解决」按钮要求 `status === 1`（`order/index.vue:132`、`mine/index.vue:119`），因此正常操作流程下无法点击。
2. **`order_no` 从不生成**：模型注释写“自动生成的编号”，但没有任何代码写入 `order_no`，新建工单该字段为 `NULL`，列表「工单号」列为空。
3. **日志字段名不一致**：后端 `work_order_log` 的备注字段是 `comment`；`frontend/src/views/wo/order/index.vue:280` 读的是 `log.remark || log.content`，所以列表页详情抽屉永远不显示日志备注；`mine/index.vue:185` 读 `log.comment` 是正确的。
4. **新建工单可能直接返回 400**：`form_orig.expect_time = ''`（`order/index.vue:371`），而 `WorkOrderSerializer` 的 `expect_time` 是 `DateTimeField(allow_null=True, allow_blank 未开启)`；DRF 3.17 的 `DateTimeField.to_internal_value('')` 会走完所有格式后抛 `invalid`。即用户不选期望时间时，新增会失败。
5. **`assign/solve/close` 没有细粒度权限**：`perm_map` 只覆盖 4 个基础 action，这三个动作只校验登录（`common/permissions.py:53-55`）。
6. **状态流转缺少前置校验**：`solve/close` 都能把已关闭工单改回 2，或重复关闭刷新 `close_time`。
7. **主表更新与日志插入无事务**：`assign/solve/close` 都是 `row.save()` 后再 `WorkOrderLog.objects.create(...)`，中间失败会留下“改了状态但没有日志”的脏数据。
8. **前端未做按钮权限**：三个工单页面的按钮都没有 `v-perm`，权限完全依赖后端；但如第 5 条所述，三个流转动作后端也没做细粒度校验。
